# RescueAI

AI-powered job failure detection, diagnosis and recovery platform (portfolio project).

**Status:** persistence and job-management API complete. Jobs are validated, stored in PostgreSQL
(with attempts, analyses, recovery actions, audit and outbox tables), and can be created, listed and
inspected. **Nothing executes jobs yet**: workers, retries, the recovery engine and AI analysis
are later phases, so new jobs stay `PENDING`.

## Prerequisites

Docker (Compose v2), Python 3.12, [uv](https://docs.astral.sh/uv/). On Windows use **WSL2 (Ubuntu)**
with Docker Desktop's WSL integration, and keep the project in the Linux filesystem.

## 1. Build and start the stack

```bash
cp .env.example .env     # set POSTGRES_PASSWORD, and the SAME value inside DATABASE_URL (letters/digits only)
docker compose up --build -d
docker compose ps        # postgres, redis, api: healthy.  migrate: Exited (0)  <- expected, it is one-shot
docker compose logs migrate    # shows "Running upgrade -> 7ae8b6bcad33, initial schema"
```

Start order: `postgres` + `redis` healthy -> `migrate` runs `alembic upgrade head` and exits ->
`api` starts. Migrations run in their own container so several API replicas can never race.

## 2. Verify each service

```bash
docker compose exec postgres pg_isready -U rescueai -d rescueai
docker compose exec redis redis-cli ping                               # PONG
docker compose exec postgres psql -U rescueai -d rescueai -c '\dt'     # 6 tables + alembic_version
curl -i localhost:8000/api/v1/health                                   # 200, database + redis "ok"
```

## 3. Try the API  (interactive docs: <http://localhost:8000/docs>)

```bash
# Create (202 Accepted + Location header). The idempotency key makes retries of this call safe.
curl -i -X POST localhost:8000/api/v1/jobs -H 'content-type: application/json' -d '{
  "job_type": "etl", "idempotency_key": "order-1001",
  "payload": {"source_dataset": "orders_raw", "target_table": "orders_clean"}}'

# Same key + same request -> 200 and "Idempotent-Replayed: true" (no new job).
# Same key + DIFFERENT request -> 409 idempotency_conflict.

curl 'localhost:8000/api/v1/jobs?status=PENDING&job_type=etl&limit=10&offset=0'
curl localhost:8000/api/v1/jobs/<job-id>
curl localhost:8000/api/v1/jobs/<job-id>/attempts
```

| Endpoint | Success | Errors |
|---|---|---|
| `POST /api/v1/jobs` | 202 (new), 200 (idempotent replay) | 409 key reused for a different request, 422 invalid |
| `GET /api/v1/jobs` | 200 `{items,total,limit,offset}` | 422 bad filter/pagination |
| `GET /api/v1/jobs/{id}` | 200 | 404, 422 (malformed id) |
| `GET /api/v1/jobs/{id}/attempts` | 200 (oldest first) | 404 |
| `GET /api/v1/health` | 200 | 503 |

Job types: `api_call`, `etl`, `report` (each with its own strictly validated payload; see
`/docs`). Every error uses one shape:
`{"error": {"code", "message", "correlation_id", "details"?}}`.
Filters: `status`, `job_type`, `created_after`, `created_before` (timezone required), `limit`
(1-100, default 20), `offset`.

## 4. Database migrations (Alembic)

```bash
uv run alembic upgrade head                    # apply all migrations (also: docker compose run --rm migrate)
uv run alembic current                         # which revision is the database at?
uv run alembic history --verbose
uv run alembic downgrade -1                    # undo the last migration   (DESTROYS data in dropped tables)
uv run alembic upgrade head --sql              # print the SQL instead of running it (for review / DBAs)
uv run alembic revision --autogenerate -m "describe change"   # then REVIEW and edit the generated file
uv run alembic check                           # fails if the models and migrations have drifted apart
```

Rules: never edit a migration that has been applied anywhere shared; add a new one. Always review
autogenerated files (they cannot see triggers, CHECK-constraint changes or data migrations).

## Data model (summary)

`jobs` 1--N `job_attempts` (execution history, never deleted: FKs are `RESTRICT`);
`jobs` 1--N `failure_analyses`, `recovery_actions`; `audit_events` (append-only, enforced by a
trigger) and `outbox_events` (written in the SAME transaction as the job; a later relay
publishes them to Redis). Statuses and types are `VARCHAR` + named `CHECK` constraints.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `relation "jobs" does not exist` | Migrations have not run. `docker compose run --rm migrate` (or `uv run alembic upgrade head` on the host). |
| `migrate` exited non-zero; `api` never starts | `docker compose logs migrate`. Usually a wrong `DATABASE_URL`/password or an unreachable database. |
| `Can't locate revision identified by '...'` | The database was migrated by a different version of the code. Use matching code, or reset dev data (`docker compose down -v`). |
| `Target database is not up to date` when autogenerating | `uv run alembic upgrade head` first, then generate. |
| Integration tests: `permission denied to create database` | `ALTER ROLE <user> CREATEDB;` (superuser). |
| Integration tests: connection refused | Start PostgreSQL/Redis and export `DATABASE_URL` / `REDIS_URL`. |
| `422` on a request you think is valid | Read `error.details[].loc` and `msg`: payloads are strict (`"500"` is not an int; unknown fields are rejected). |
| `409 idempotency_conflict` | That key was already used with a different job type/payload/max_attempts. Use a new key. |
| `503 service_unavailable` | The database is unreachable; check `/api/v1/health` and `docker compose ps`. |
| Port, password, WSL and line-ending issues | See the previous troubleshooting entries: `port is already allocated` -> set `POSTGRES_HOST_PORT`; password changed after first `up` -> `docker compose down -v` (deletes data); Docker missing in WSL -> enable WSL integration; edit `.env` with `nano`, not Notepad. |

## Known limitations

* No authentication yet (idempotency keys are therefore **globally** unique; they become per-owner
  when users exist). Audit events record callers as `ANONYMOUS`.
* No execution: jobs stay `PENDING`; `outbox_events` rows accumulate unpublished until the relay exists.
* Payloads are returned by the job-detail endpoint. Payload schemas therefore must never carry
  credentials (enforced for URLs today); reference secrets by name instead.
* `api_call` jobs accept any http(s) URL. Before they are *executed*, an allow-list / SSRF guard is required.
* Pagination is `limit/offset` with an exact `total` (simple, fine at portfolio scale); very deep
  pages and `count(*)` get slower as the table grows, where keyset pagination would be the upgrade.
* No request-body size limit or rate limiting yet.
* The state-transition table and DB-level transition enforcement arrive with the first code that
  changes job status. Today the database enforces *state invariants* (e.g. final states have `completed_at`).
* Redis has no password in the dev Compose file (bound to localhost only).
* The Docker image has not been built in the environment where these phases were written.
